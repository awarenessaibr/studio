# Deep Review: Animation Capabilities in studio-layers

This is a **layer-based 2D animation system** with three distinct animation layers stacked on top of each other: (1) per-layer keyframe interpolation, (2) a procedural character-rig generator that *bakes* keyframes, and (3) an LLM-driven director that selects from a fixed vocabulary. Below is a walkthrough of what each system can actually do, with references to where the code implements it.

---

## 1. Core data model (`_.js` → `makeLayer`, `normalizeComposition`)

A **composition** is:

```js
{ version, id, name, width, height, duration,
  referenceLayerId, characters[], layers[] }
```

Every **layer** carries:

| Field | Range | Notes |
|---|---|---|
| `x, y, w, h` | percent of canvas (-100..200 for x/y, 1..300 for w/h) | All animation is expressed in this percent space |
| `rotation` | -3600..3600 degrees | |
| `opacity` | 0..1 | |
| `z` | -1000..1000 | Draw order |
| `fit` | `contain` / `cover` | |
| `frames[]`, `spriteFps`, `spriteMode` | 1–60 frames, 1–30 fps, `loop`/`pingpong`/`once` | Sprite animation |
| `role` | `background, midground, ground, foreground, character, character-part, prop, effect` | |
| `part, group, variant` | strings | Rig metadata (v3) |
| `recolorEnabled/Color`, `outlineEnabled/Color/Width` | | Runtime pixel effects |
| `keyframes[]` | max 400 per layer | `{time, x, y, w, h, rotation, opacity}` |

**Keyframe interpolation** (`getLayerStateAtTime`) is **linear per-property** with no easing — blending is done by the *generator*, not the renderer. Every animated property has its own timeline. A layer can have 0, 1, or many keyframes; no keyframes means static.

**Animation time is shared** (`this.animation.currentTime`), and `applyAnimationTime(t)` writes the interpolated state directly into DOM `style.left/top/width/height/opacity/transform`.

## 2. Preset library (`applyPreset`, `_.js`)

The studio ships **10 procedural presets**. They are all *keyframe generators*, not stored code — calling `applyPreset` replaces a layer's keyframes.

| Preset | Keyframes | What it emits | Parameters (default) |
|---|---|---|---|
| `breathe` | 3 | w/h × 1.02 at midpoint | — |
| `idle` | 4 | y ± 0.5%, rotation ± 0.4° | — |
| `sway` | 9 | sinusoidal x + rotation, 1 cycle | `amplitude` (2), `tilt` (3) |
| `walk` | 5 | linear x from `startX` → `endX`, with ± 1.5° tilt at quarters | `startX`, `endX` |
| `float` | 5 | y bob ± `distance` | `distance` (2) |
| `flicker` | 12 | random opacity 0.55–1.0 | — |
| `drift` | 2 | linear x + `distance` | `distance` (15) |
| `pulse` | 3 | w/h × scale at midpoint | `scale` (1.06) |
| `fadeIn` | 3 | opacity 0 → base over first 800 ms | — |
| `parallax` | 3 | x ± `distance` swing | `distance` (4) |

Parameters are validated and clamped by `PARAM_RULES` on the server side (`server.js`) and by `normalizePresetParams` on the client. So the LLM cannot produce an out-of-range `amplitude=200`.

This is the **entire animation vocabulary** for layer-level motion. There is no path-tweening, no easing curves, no masks, no separate scale-X/scale-Y, no color animation, and no visibility toggles. Anything more complex must be expressed as keyframes generated procedurally.

---

## 3. Sprite animation (`_spriteState`, `_.js`)

Per-layer frame-by-frame animation exists (`frames[]` arrays) but is **not generated by the studio** — it comes from imported compositions. `spriteFps` and `spriteMode` control playback:

- `loop` — modular time
- `pingpong` — bounce over `2n-2` period
- `once` — clamp to last frame

The renderer swaps `img.src` during `applyAnimationTime` and during export (`renderExportFrame`). This is important because the *v3 rig* never uses sprites for mouth shapes — it uses **opacity crossfades** between pre-baked mouth PNGs instead. (See §5.)

## 4. Auto-alignment (`matchImageToReference`, `_.js`)

This is the mechanism that turns a ZIP of cutouts into a *placed* scene. It is **not** an animation feature but a positioning tool — however it directly enables animation because every layer needs a canonical (x, y, w, h) before keyframes make sense.

The algorithm:

1. Downscale reference to `MAX_MATCH_EDGE = 640` px, run `alphaBounds` and `templateSamples` on each layer at 12 scales (`0.25 … 2`).
2. Score each candidate with a composite of **color error** + **gradient error** + **alpha penalty**. The reference is "un-backgrounded" only if the border is < 5% transparent (`estimateReferenceBackground`).
3. Keep top-6 seeds per scale, refine locally at 5 sub-scales, then report the best match with an `alternative` for ambiguity.
4. Verdicts: `matched` (score < 0.18), `ambiguous`, `unmatched`.

`applyAmbiguous: true` uses the best guess; `confirmExact: true` auto-confirms exact matches. This is what the ZIP-import flow (`submitArchive`) calls.

## 5. Character rig v2 vs v3

Two rig versions live side by side; **v3 supersedes v2** but v2 still runs for older imports.

### 5a. v2 (`applyCharacterAnimationV2`)

Simple part-based rig. `CHARACTER_PART_KEYS` = `face, eyes, pupils, highlights, eyelids, brows, mouth, jaw, teeth, tongue, mustache, beard, head, body, hands, ears, neck, fx`.

- Face base cover is generated client-side by `createCharacterCover` — it samples skin color around the eyes (`sampleCharacterSkin`), draws a filled face silhouette, then paste-composites feature layers. This is the "cheap face plate" that v3 replaces.
- Animation is: eye-scale × `eyeScaleBase`, pupil offset by `gaze`, `talkWave` sine on mouth/beard, `breathe` sine on head/body, `blinkAt` sine-based on eyes/pupils.
- Expression drives **scale-and-offset** heuristics, **not** variant switching.

### 5b. v3 (`applyCharacterAnimationV3`) — the flagship

This is a proper cutout rig. Its central idea: **variant layers share one bounding box and switch through opacity keyframes**, so no new animation channels are needed. The renderer, exporter, SVG writer, and agent protocol all work unchanged.

**Generators inside `applyCharacterAnimationV3`:**

| Channel | Function | Details |
|---|---|---|
| **Blink** | `blinkEvents` / `blinkAt` | Mean interval `60000/blinkRate`; length 185–260 ms; 15% double-blink; `smoothstep(0,1)` on open/close edges. With eyelids: crossfade `half` ↔ `closed`. Without: scale eye height and drop pupil. |
| **Gaze** | `saccades` / `gazeAt` | Holds 850–2600 ms, blend 95 ms, micro-jitter `0.012·sin(t/2900)`. Range `0.34` if `eyeWander`, else `0.1`. |
| **Speech** | `textToVisemes` / `buildTalkTrack` | Grapheme → viseme map (`a e i o u mbp fv l wq rest`), base 78 ms per letter / rate, commas 2.6×, periods 3.8×, merges same-viseme segments within 45 ms. Continuous `talk` mode uses a looping viseme sequence. |
| **Viseme crossfade** | `visemeWeightsAt` / `mouthWeightsAt` | 55 ms fade between adjacent visemes. Missing variants fall back to `rest`. |
| **Expressions** | expression maps | 5 expressions map to eye-scale, brow-variant, mouth-default-viseme, pupil-Y, mouth-Y. |
| **Head sway** | `headAt` | 2 sine components (6900 ms + 2900 ms) scaled by `headSway` 0–1; `dx/dy` offsets. |
| **Breathing** | `breatheAt` | Sine over 4300 ms scaled by `breatheAmount`; body anchors at the bottom. |
| **Pulse** | `pulseAmount · sin(t/720)` | Applies to eyes/pupils/highlights/eyelids (scale 2.6%) and beard (4%). |
| **Secondary lag** | `secondaryTilt` | Beard 180 ms, mustache 120 ms, head 90 ms behind the head rotation. |
| **Jaw** | open mouth | `h × (1 + openAmount × 0.18)` + Y drop. |
| **Mustache** | open mouth | Y + 0.35·opening, slight height squash. |

**Keyframe sampling** is deliberately non-uniform:

- Regular step = 60–120 ms (capped at ~380 samples)
- Blink edges injected at `-30, 0, +30, +62, close-95, close-40, close`
- Viseme edges at `-25, 0, +55, end-55, end, end+25`
- Saccade edges at `start, start+95`

This is why a v3 character produces **200–380 keyframes per layer** while layer-level presets produce 2–12. It is also why v3 is expensive to store (each layer's keyframe array is a full timeline).

**Reference layer visibility:** while any v3 rig is applied, `syncRigReferenceVisibility()` hides the reference layer; clearing the animation restores it (`clearCharacterAnimation`).

**Default presets** (`CHARACTER_ANIMATION_PRESETS`) include `talk-well-met`, `talk-entao-ta-neh`, `idle`, `happy`, `sad`, `surprised`, `angry`, `blink-test`, `talk-loop`, `mouth-a-qa`. They are just argument bundles to `updateCharacterSettings`.

## 6. Effects (`layerEffectFilterMarkup`, `_.js`)

Per-layer pixel effects, applied as SVG filters on the DOM and re-implemented in canvas during export:

- **Recolor** — flood-fill visible pixels with a solid color (`feFlood` + `feComposite`).
- **Outline** — dilate alpha, flood the outline color, composite under the original. Radius in *scene pixels* is scaled to the displayed width in `loadExportAssets` (cap 32 px). GIF/MP4 export uses a `dilateAlpha` deque dilation — the same algorithm as the SVG `feMorphology`, so screen and export match.

No animation is wired to effects, but they participate in `hasLayerEffects` so they are re-applied every frame.

## 7. LLM animation director (`server.js` → `generateDirectorIdeas`)

Two-stage pipeline:

### Stage 1 — Vision
`buildVisionPrompt` asks a vision model (`granite3.2-vision:2b` by default) to return `{subject, setting, mood, palette, keyElements, motionCues, depthNotes}`. The image is downscaled (`createVisionImage`, 768 max edge, JPEG 0.82). It uses the reference layer, or the first layer if none.

### Stage 2 — Writer
`buildWriterPrompt` produces the JSON proposal schema. Key constraints enforced by `normalizeDirectorProposals`:

- `layerId` must resolve to a catalog alias `L01…`, a real id, or a unique name.
- `preset` must be in the vocabulary.
- `params` are clamped by `normalizePresetParams`.
- Each proposal gets 2–12 commands.
- Character commands (`characters[]`) are normalized by `normalizeProposalCharacters`; those layer IDs are then **stripped from the command list** so the same layer isn't driven twice.

**What the LLM can actually emit:**

- Layer-level: any preset + any allowed params.
- Character-level: `expression, blink, blinkRate, blinkAmount, talk, talkIntensity, talkSpeed, gazeX, gazeY, eyeWander, breathe, breatheAmount, headSway, pulseAmount, saccade, speechText, speechRate, speechStart, mouthPose`.
- It **cannot** invent new presets, cannot add custom easing, cannot edit effects, and cannot access the existing keyframes (the catalog is static geometry only — see `buildDirectorCatalog`).

The `proposals.json` for Curupira is a concrete example: `{layerId: layer-16-…, preset: 'drift', distance: 2}` for the boy and `{preset: 'walk', startX: 50, endX: 60}` for the fox. These are valid but *do not* overwrite the existing pulse-like keyframes until the user presses **Apply**.

### Organizer
`organizeSegments` uses a vision model to read *thumbnails* and propose `{id, name, group, role}` per segment. This is how `segmentGroup` is populated. It supports both Ollama and one remote OpenAI-compatible endpoint via env vars.

## 8. Export pipeline (`exportImage`, `exportVideo`, `exportGif`, `exportSvg`)

All exports go through `renderExportFrame`, which:

1. Sorts layers by z, with reference first.
2. Calls `getLayerStateAtTime` to interpolate keyframes (linear).
3. Handles `contain` vs `cover` with correct source cropping.
4. Applies sprite frame lookup.
5. Rotates around center.

`loadExportAssets` caches one preprocessed image (or canvas) per layer, applying recolor/outline at load time with a **per-layer pixel budget** so exports stay bounded.

| Format | Limits | Notes |
|---|---|---|
| PNG | 4096 max edge, 24 MP total | Strips the reference, shows all layers |
| WebM/MP4 | `MediaRecorder`, 1920 max edge | Real-time recording at 30 fps (not deterministic timing) |
| GIF | 480 max edge, 100 ms/frame | Custom LZW + 6×6×6 palette + skin/beard ramps (`buildGifPalette`) |
| SVG | Unlimited | One `<image>` per layer, no keyframe baking |
| JSON | — | `createExportSnapshot` clones layer + keyframes |
| Agent spec | — | `layer-studio/agent/v1` with vocabulary lists |

`exportAllSegments` and `exportSegmentGroup` package raw layer PNGs into a **stored (uncompressed) ZIP** via `buildStoredZip` (CRC32 table inline). The group export produces two PNGs — transparent and with-final — by re-running `renderExportFrame` with two `exportBackground` values.

## 9. Tooling layer

The repo ships several Node/Python scripts that all use the same pipeline:

- `composition-generator.js` — walks a folder, classifies by regex, and emits a `.composition.json`. Sprite detection: 2–8 numbered character/character-part files. Scatter detection: 3+ props. Otherwise one layer per file. Reference auto-detected by `atacama|reference|assembled|final` or largest area.
- `place-character.js` — merges a character composition into a scene at a given height/x/bottom. Scales bbox, offsets keyframes, prefixes ids, updates `meta.placedCharacters`.
- `apply-beards-rig.js` — idempotent re-wiring of the Beards asset pack (v3 rig). Removes old `beards-*` layers, reads `assets/manifest.json`, rebuilds `character.parts`, writes `composition.json` and `beards-agent.json`.
- `build-beards-assets.py` — generates the **entire 41-file Beards asset pack** from the final image: face plate via silhouette ∩ outer mask (with nose line preserved), clean eye whites by inpainting the pupil, procedural eyelids (`half`/`closed`), 4 brow variants by shear, 13 mouth visemes with lip/tongue/teeth geometry, mustache with the lip line removed, ears recovered from the reference.
- `render-beards-preview.js` — CDP-driven renderer that stages the studio, renders 240 frames, runs ffmpeg, and writes contact sheets (`beards-expressions.png`, `beards-mouths.png`, `beards-blink.png`, `beards-filmstrip.png`).
- `export-beards-animations.js` — bakes the 10 animations in `animations.json` into standalone compositions under `data/projects/Beards/compositions/`.

The Beards project is therefore the **reference v3 implementation**: it demonstrates the entire range of expressive animation (speech, blinks, gaze, saccades, breathing, head sway, expressions, viseme crossfades, pulse, mustache secondary motion, jaw open) as *ordinary keyframes* on standard layers.

## 10. The Curupira composition — what's actually animated

Looking at the attached files:

```jsonc
// fox layer, ~z 78
keyframes: [
  { time: 0,     w: 15.088 },   // pulse
  { time: 5000,  w: 15.390 },   // scale up 2%
  { time: 10000, w: 15.088 }
]
// red-haired-boy layer, ~z 90
keyframes: [
  { time: 0,     w: 12.139 },   // pulse
  { time: 5000,  w: 12.867 },   // scale up 6%
  { time: 10000, w: 12.139 }
]
```

So the current state is **two pulse presets** — nothing else. The `proposals.json` suggests `drift` (boy) + `walk` (fox) instead, but the LLM's view of the scene (`buildDirectorCatalog`) doesn't include the existing keyframes, only static geometry. That's why the LLM's suggestions don't "react to" the pulse.

The other 30 layers (ferns, fireflies, footprints, misty background, tree trunks, branches, loincloth, illegible prop, missing overlays) have **no keyframes**. Each is a static positioned cutout. Fireflies are prime candidates for `flicker` or `pulse`; ferns for `sway`; footprints for `fadeIn`; the trunk and branches for `parallax` or `sway`.

There is also a **missing/illegible** group of layers (`033-missing-03`, `034-missing-02`, `035-missing-01`, `003-illegible`) — placeholder layers that the segmenter couldn't resolve. These are positioned over the canvas but do nothing useful; they are probably deliberately left visible so the user can edit them.

## 11. What is *not* possible (and why)

| Wish | Why not |
|---|---|
| Nonlinear easing | `getLayerStateAtTime` interpolates linearly; only the *generator* shapes the curve via more samples |
| Animated color / opacity effects | `recolor` and `outline` are static per layer |
| Animated masks / clipping | No mask layer type |
| Rigging a non-character object (e.g., a bird with wings) | Rig detection is regex+geometry against `CHARACTER_PART_KEYS`; there is no generic skeleton |
| Multi-character scenes | `characters[]` supports up to 12, but each rig uses its own bbox and `hidden` list; the server's writer prompt accepts them, and `normalizeProposalCharacters` handles duplicates — but the placeholder UI only renders the first one's inspector in practice |
| Truly arbitrary animation from the LLM | The LLM has no way to write keyframes directly — it must pick a preset or a character setting |

## TL;DR

The animation system is built from **four composable primitives**, in ascending expressiveness:

1. **Sprite playback** — discrete frames, 1–30 fps, three modes.
2. **Keyframe interpolation** — six properties (x, y, w, h, rotation, opacity) per layer, linear between up to 400 frames.
3. **Preset generators** — 10 named procedural routines that emit keyframes for a single layer; params are clamped server-side.
4. **Character rig v3** — a *keyframe compiler* that consumes the rig's settings (blink, gaze, talk, expression, breathe, headSway, pulse) and produces per-layer timelines of 200–380 keyframes each, with variant crossfades for eyelids, brows, and mouths.

On top of that sits the **LLM director**, which only ever selects from presets and character-settings — it can't write raw keyframes. The **Beards** project is the proof-of-concept: a full expressive face (13 visemes, 4 brow poses, 2 eyelid states, saccades, blinks, double-blinks, breathing) generated entirely as ordinary keyframes from a small settings dictionary. The **Curupira** project is the front-door demo for the *new* workflow: ZIP-import → auto-align via template matching → vision-model segment organization → LLM proposals → one-click preset application.
